前言:

這個範例並不是在教怎麼寫 Clean Code, 也不是什麼正規的軟體開發該做的事, 甚至這個範例的修改非常 dirty. 這個修改方法也不是真的零風險, 但已經盡可能降低所有可能問題與障礙, 這方法是為了解決遺留系統要重構底層物件與演算法時必然會遭遇的問題, 適用於可重複執行而不影響輸出的程式碼.

如果你有遭遇:

* 流程都會與 Global 變數綁定  
* 餵資料的流程跟 UI 徹底綁定  
* 單元測試的測試框架不適用遺留系統  
* 相關流程重構需要時間. 重構底層遙遙無期  
* 不修改就無法學習, 沒有測試就沒辦法安全的學習  
* 驗證修改需要能產生龐大的動態的測試資料  
* 驗證修改需要自動化測試, 不然人力追趕不上

那這方法也許適合你.

但是如果這些情況讓你無法接受:

* 過程中有部分步驟是在無測試下修改, 而你仍然堅持要有單元測試才進行修改  
* 過程中會產生部分 dirty code, 而你堅決不允許 Source Code 再寫出任何 dirty code  
* 建立自動化測試以後, CI/CD 也許會頻繁亮燈, 而你無法接受持續被燈號 & Member 轟炸

那這個方法不適合你.

方法說明:

遺留系統特色:

* 程式設計不良, 過去的設計無法支撐越來越龐大的商業邏輯  
* 沒有良好軟工實踐, 過去規格, 測試, 版控不完整, 導致程式碼不完全正確

以理論的角度來看, 它不光是要設計能負荷既有的商業邏輯的程式碼, 更因為程式碼不完全正確, 需要進行一連串的考古行為. 而這兩個問題會導致重構難度等比級數提升, 因為你不光要設計, 更要同時間抵抗中途發現的隱藏規格.

為了應對這些問題, 這個方法主要分成三個步驟, 分別為:

1. 將 UI 的程式碼分離, 抽取 Controller  
2. 使用 Controller 建立測試, 複製一份 Source Code 進行差異比對測試  
3. 以對比測試的範圍為基礎, 開始進行修改, 測試, 學習的自動化迭代過程

每個遺留系統都是一個龐大的問題空間(Problem Space), 因為空間龐大, 遠超過人類理解跟學習能接受的時間跟負荷. 這個方法之所有有效,  是因為這三個步驟採取的策略就是在任何時間點都不直接搜索遺留系統的問題空間(Problem Space),而是搜索遺留系統的問題子空間.在縮減問題空間的同時, 搭配 CI/CD 加快 修改, 測試, 學習的過程,讓人們盡早的跨越遺留系統的理解跟學習成本.

將這三個步驟做的事情進行分析:

1. 將 UI 的程式碼分離, 抽取 Controller  
   將抽取 Controller 的工作內容, 只是增加一個 Controller 的 Class, 並將 UI 存取 Data 的行為改為轉呼叫 Controller. 抽象來看整個流程只是不斷的進行進行 Move, Assign. 你思考的只是 UI 處理 Data 的變數與時機, 此時你處理的問題縮減為順序問題.

2. 使用 Controller 建立測試, 複製一份 Source Code 進行差異比對測試  
   當你有一份舊 Source Code 可以隨時進行差異比對測試, 當測試結果出現錯誤, 你處理的問題選項縮減為 "自己修改錯誤", "兩者皆錯". 你的思考跟要解決的問題被限縮在 “自己何處修改錯誤?”, “舊的程式碼是不是本來就錯的?”, 追查問題跟改正問題的速度會提升很多.  此時你處理的問題是在 “你修改的程式碼” 跟 “舊的程式碼” 兩者產生差異的空間進行搜索.  
     
3. 以對比測試的範圍為基礎, 開始進行修改, 測試, 學習的自動化迭代過程  
   當差異比對測試持續進行, 修改, 測試, 學習的過程開始迭代, 舊程式碼的錯誤開始被挖掘出來並清除, 並開始重新設計底層物件與演算法. 透過這些建立的差異比對測試, 能讓你的設計取得回饋並修正. 由於設計必須相容舊程式碼, 此時你的設計問題其實是在以舊程式碼為錨點進行周圍空間空間擬合與搜索.

總結來說:

* 步驟1 透過將程式問題縮減為順序問題  
* 步驟2 透過差異比對測試將修改問題縮減為比對問題  
* 步驟3 透過差異比對測試將設計問題縮減為空間擬合問題.

整個過程只有步驟1 是處於沒有測試覆蓋的狀況, 但步驟1 解的問題是最簡單的順序問題, 將風險降至最低. 步驟2 由於遺留系統初期沒有辦法撰寫單元測試, 所以轉為撰寫差異比對測試.步驟3 開始在有基礎測試安全網下進行重新設計, 重新設計出新的程式碼之後就可以改走現代軟體開發流程, 改為撰寫單元測試.
